# Mihomo 规则可视化生成器

## 计划书 1.0

**文档状态**：规划阶段，不包含实现代码

**适用范围**：使用 Mihomo 内核的桌面端与移动端客户端

**后续方向**：非 Mihomo 客户端通过订阅转换适配，本阶段不实现

---

## 一、项目定位

### 1.1 产品目标

为不会编写 Mihomo 远程配置和规则的用户，提供可视化的分流配置界面，生成可自动更新的 Mihomo 订阅/远程配置链接。

用户只需要提供原始订阅地址并选择规则归属，系统负责生成策略组、规则顺序、规则提供者和最终链接。

### 1.2 当前产品承诺

- 支持使用 Mihomo 内核的桌面客户端。
- 支持使用 Mihomo 内核的移动客户端。
- 输出以订阅链接或远程配置链接为主，不依赖客户端本地覆写功能。
- 支持 Mihomo 需要的 `RULE-SET`、`rule-providers`、`GEOSITE` 等能力。
- 同一套分流意图在桌面端和移动端使用相同的生成逻辑。

### 1.3 不属于当前承诺的范围

- 不对 Surge、Quantumult X、Loon、sing-box 等非 Mihomo 内核客户端提供兼容性承诺。
- 不在当前 UI 中提供多个客户端格式选择器。
- 不在当前阶段实现非 Mihomo 原生配置导出。
- 不实现订阅转换服务本体，不建设节点托管、订阅存储或后端数据库。
- 不负责节点管理、机场服务、账号管理和完整客户端设置管理。

### 1.4 后续适配方向

后续新增独立的订阅转换适配阶段，复用当前的分流意图模型，为非 Mihomo 客户端生成目标格式。具体转换服务、支持的客户端和格式列表在后续计划中单独确定。

## 二、兼容性边界

### 2.1 兼容性判断标准

以客户端使用的内核能力为准，而不是以客户端品牌或设备类型为准。

当前目标客户端必须满足：

1. 使用 Mihomo 内核或与 Mihomo 配置语义兼容。
2. 能通过订阅链接或远程配置加载生成结果。
3. 能处理当前方案使用的规则提供者和规则类型。

### 2.2 桌面端与移动端

桌面端和移动端都属于当前范围。移动端不单独维护一套规则模型，只验证以下事项：

- 订阅链接能正常导入。
- 远程配置能正常加载。
- 策略组和规则提供者能正常显示。
- 长 URL 在目标客户端中不会被截断或拒绝。
- 规则更新和节点更新行为符合预期。

具体客户端名称只作为验证样本，不作为永久兼容清单。兼容清单应绑定 Mihomo 内核版本和实际测试结果。

### 2.3 非 Mihomo 客户端

非 Mihomo 客户端暂不进入当前 UI、生成器和验收范围。后续通过订阅转换流程适配，例如将统一的用户分流意图转换为不同客户端的订阅或配置格式。

## 三、技术路线

### 3.1 当前生成链路

```text
用户原始订阅地址
        |
        v
前端分流配置
        |
        v
Mihomo remote config / rule-providers
        |
        v
data:text/plain;base64 内联配置
        |
        v
subconverter 后端生成 Mihomo 可消费的订阅结果
```

当前继续使用 `subconverter` 作为转换后端，但产品层只承诺生成结果适用于 Mihomo 内核。后端接口中的 `target=clash` 是 subconverter 的协议参数，不扩展为其他客户端支持承诺。

### 3.2 配置控制原则

使用 `clash_rule_base=data:` 内联最小基础配置，尽量避免继承公共后端的未知默认值。基础配置至少应明确：

- `mode`。
- `port` 或必要的基础字段。
- `rule-providers`。
- `rules`。
- 当前方案需要的 DNS、局域网和安全相关默认值。

规则集优先使用 Mihomo 的 `rule-providers`，由客户端按间隔自行更新，减少后端逐条拉取规则集的压力。

### 3.3 部署边界

- 前端为纯客户端应用。
- 不保存用户原始订阅地址。
- 不保存生成的订阅内容。
- 公共 subconverter 后端只作为可选依赖，必须提示订阅地址会经过该服务。
- 允许用户填写自建转换后端地址。

## 四、分流模型

### 4.1 基础策略组

用户可以启用以下基础组：

- `🚀 节点选择`：统一入口。
- `✋ 手动选择`：匹配全部节点。
- `♻️ 自动选择`：对全部节点测速。
- `🔃 故障转移`：对全部节点执行故障转移。
- 地区组：按节点名称正则筛选指定地区。
- `🌐 其他地区`：排除已启用地区后的剩余节点组。

基础组的启用状态决定其他策略组的可选项，避免产生悬空引用。

### 4.2 灵活桶

为单个服务生成独立策略组，例如视频、AI、社交或游戏服务。用户可以为每个服务独立选择节点选择、地区、直连或其他基础组。

### 4.3 代理桶

用户选择的代理规则集共享 `🌍 代理` 策略组。

### 4.4 直连桶

用户选择的直连规则集共享 `🎯 直连` 策略组，默认优先使用 `DIRECT`，同时允许临时切换到节点选择。

可选启用 `GEOIP,CN`，用于将未被其他规则匹配的中国 IP 交给直连桶。

### 4.5 漏网之鱼

自动生成 `🐟 漏网之鱼` 策略组，并始终将 `FINAL`/`MATCH` 规则放在最后。用户不直接配置该组。

### 4.6 前置修正

可选启用局域网直连和白名单修正，并将其放在所有用户规则之前。

---

## 五、规则顺序

最终规则顺序固定为：

```text
1. 前置修正
2. 用户自定义规则
3. 灵活桶规则
4. 代理桶规则
5. 直连桶规则
6. GEOIP,CN（若启用）
7. FINAL / MATCH 兜底
```

同一桶内按预置目录的 `bucketOrder` 排序。用户不能跨桶拖拽规则，以避免破坏优先级模型。

同一规则集被同时分配到代理桶和直连桶时，必须在分配时提示并在生成前再次校验。

## 六、数据模型

```ts
interface Config {
  version: 1
  backend: string
  subUrl: string

  base: {
    manualSelect: boolean
    autoSelect: boolean
    fallback: boolean
    regions: RegionConfig[]
  }

  assignments: Record<PresetId, Assignment>
  customRules: CustomRule[]

  headModifiers: {
    localAreaNetwork: boolean
    unban: boolean
  }

  enableGeoipCN: boolean
}

type Assignment =
  | { bucket: 'proxy' }
  | { bucket: 'direct' }
  | { bucket: 'flexible' }
  | { bucket: 'off' }
```

策略组是否生成由基础配置和规则分配结果派生，不维护多个独立的 `enabled` 真相源。

规则集预置目录至少包含：

- 唯一 ID。
- 显示名称。
- 分类。
- 规则集 URL。
- 默认桶。
- 桶内排序值。
- 可选说明和显示 emoji。

## 七、用户流程

### Step 0：输入与后端

- 填写原始订阅地址。
- 选择公共 subconverter 后端或填写自建后端。
- 显示隐私提示：生成链接包含原始订阅地址。

### Step 1：基础策略组

- 选择手动、自动、故障转移策略组。
- 选择地区组。
- 可选进行节点名称预览。
- 对 0 命中的地区组给出警告，并禁止生成会退化为 `DIRECT` 的空组。

### Step 2：规则集分配

- 按分类浏览预置规则集。
- 将规则集分配到不启用、代理、直连或灵活桶。
- 显示规则集说明、来源和当前归属。

### Step 3：自定义规则

支持：

- `DOMAIN-SUFFIX`。
- `DOMAIN`。
- `DOMAIN-KEYWORD`。
- `IP-CIDR`。
- `IP-CIDR6`。
- `PROCESS-NAME`。

自定义规则只能分配到代理桶或直连桶，并提供格式校验和删除能力。

### Step 4：输出与检查

- 生成 Mihomo 订阅/远程配置链接。
- 展示生成的配置文本。
- 展示策略组、规则集和 URL 体积统计。
- 执行结构校验和可用性检查。
- 提供复制链接和打开链接的入口。

## 八、生成契约

### 8.1 生成内容

生成器负责：

1. 生成 Mihomo 基础配置。
2. 生成策略组。
3. 生成 `rule-providers`。
4. 按固定顺序生成 `rules`。
5. 将配置编码为 URL-safe Base64。
6. 组装 subconverter 请求地址。

### 8.2 后端参数

必须显式控制会影响节点名称和策略组命中的参数，例如：

- `add_emoji`。
- `remove_old_emoji`。
- `new_name`。
- `insert`。

避免同一配置在不同公共后端上产生不同节点名称或不同策略组命中结果。

### 8.3 规则提供者

每个远程规则集对应一个稳定的 provider ID，包含：

- `type: http`。
- `behavior`。
- 规则集 URL。
- 本地缓存路径。
- 更新间隔。

规则引用统一使用 `RULE-SET`，需要时使用 Mihomo 支持的内联规则类型。

## 九、防错与验证

### 9.1 生成前校验

- 组名唯一性。
- 组名、规则值和正则中的分隔符注入校验。
- 策略组引用完整性。
- 地区组命中数检查。
- 规则集冲突检查。
- 用户正则合法性检查。
- URL 长度提示或拦截。

### 9.2 生成后校验

优先解析后端返回的 YAML，检查：

- 目标策略组存在。
- `rules` 不为空。
- `rule-providers` 结构完整。
- `MATCH`/`FINAL` 兜底存在且位于末尾。
- 代理、直连和灵活组引用均可解析。

如果目标后端不允许浏览器跨域访问，则降级为打开链接自查，并显示明确检查项。

### 9.3 Mihomo 移动端验证

验收时至少覆盖一类 Mihomo 内核移动客户端，重点验证：

- 长链接导入。
- 远程配置更新。
- 规则提供者下载和更新。
- 节点名称和地区正则命中。
- 策略组切换。
- 无节点命中时不会静默退化为直连。

## 十、隐私与安全

- 原始订阅地址只保存在当前页面内存中。
- 生成链接包含原始订阅地址，复制时必须提示不要公开分享。
- 公共后端可能记录访问日志，界面必须明确提示。
- 配置导出和分享功能不得默认包含原始订阅地址。
- 不在本项目服务器保存用户配置和节点信息。

## 十一、阶段划分

### 阶段一：Mihomo MVP

- 完成 Step 0–4 基础流程。
- 完成基础组、灵活桶、代理桶、直连桶和漏网之鱼。
- 完成前置修正和自定义规则。
- 使用 `clash_rule_base=data:` 内联基础配置。
- 使用 `rule-providers` 管理远程规则集。
- 完成生成前校验和基础生成后校验。
- 完成桌面端与移动端的 Mihomo 兼容性验证。
- 提供 ACL4SSR 预置目录的最小可用集合。

### 阶段二：可用性增强

- 一键预设方案。
- 节点名称预览。
- 流量路线说明。
- 更完整的 YAML 校验。
- 配置 JSON 导入/导出。
- 更细致的规则内容重叠分析。

### 阶段三：分享与配置管理

- 不含原始订阅地址的配置分享。
- 配置版本管理。
- 可选的本地加密保存。
- 预设目录和规则源管理。

### 阶段四：非 Mihomo 订阅转换适配

本阶段不属于 1.0 实现范围，后续单独规划：

- 复用统一的用户分流意图模型。
- 通过订阅转换生成目标客户端格式。
- 增加目标客户端能力差异处理。
- 增加各格式的独立校验和测试矩阵。

## 十二、1.0 验收标准

1. 用户可以在不编写配置文本的情况下完成一次分流配置。
2. 生成结果可被目标 Mihomo 桌面端加载。
3. 生成结果可被目标 Mihomo 移动端通过链接加载。
4. 规则集更新不需要用户重新编辑规则内容。
5. 不产生悬空策略组引用。
6. 不产生 0 命中地区组的静默直连风险。
7. `FINAL`/`MATCH` 始终存在并处于规则末尾。
8. 组名和规则值中的非法分隔符会被拦截。
9. 原始订阅地址不会写入持久化存储。
10. 非 Mihomo 客户端不出现在 1.0 的兼容性承诺和验收清单中。

## 十三、待确认事项

- 1.0 要求支持的 Mihomo 最低版本。
- 首批移动端验证样本及其导入方式。
- 公共 subconverter 后端的默认选择和故障切换策略。
- 是否在 MVP 中启用完整 `rule-providers`，还是先保留规则集直连方案。
- 预置规则源是否仅使用 ACL4SSR，或允许后续切换其他来源。
- 移动端对超长 URL 的实际上限。

---

## 十四、范围结论

1.0 的核心不是“所有客户端通用”，而是“桌面端和移动端的 Mihomo 内核客户端使用同一套分流模型和生成链路”。

非 Mihomo 客户端通过后续订阅转换实现，当前不增加相关 UI、格式、适配器或测试负担。
